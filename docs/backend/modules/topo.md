# 拓扑画布模块（topo_mgr）

**路由前缀：** `/api/topo/`
**App Label：** `topo_mgr`

---

## 职责

把「项目组 × 渠道 × 环境（× 地域）」下的接入链路画成一张可编辑的图：加速域名 →
解析记录 → GA / 负载均衡 → 主机，附带证书落在哪台机上。目的不是画图好看，而是
让「这条链路经过哪些东西」「这台机下线会断哪个域名」有一个能当场看懂的答案。

| 概念 | 说明 |
|------|------|
| `TopoCanvas` | 一张画布，绑定一组维度（项目组/渠道/环境/地域）；同组合允许多张，用 `slug` 区分 |
| `TopoNode` | 画布上的节点，分引用型（`source=ref`）与外部型（`source=external`）；`attrs` 存展示细节，已被识别的键见模型注释（当前只有 `kind_label`） |
| `TopoEdge` | 节点之间的有向关系，`relation` 带语义（解析/后端/源站/回源/落地/挂载/关联）；`source_handle`/`target_handle` 记走线从哪一侧出入 |

### 画布不是第五套资产台账

节点分两类，判据是「平台有没有这个东西的模型」：

- **引用型**（`server` / `domain` / `dns_record` / `certificate`）：只存
  `kind + ref_id`，名称、IP、状态一律**实时读**原表。不存快照——主机改了名、证书
  快过期，图上必须当场看见；存快照就变成又一份会过期的台账，而看图的人要的正是
  「现在长什么样」。实体被删则节点标为已失联（`ref.exists=false`）并留在图上，不
  静默消失，否则链路凭空断开且没人知道断在哪。
- **外部型**（GA 加速器、各家 LB、CDN、WAF…）：平台尚未建模的云资源，手工录入
  `label + attrs`。将来 cloud_mgr 补上负载均衡模型，这类节点可就地升级成引用型
  （改 `source/kind/ref_id`，边不用动）。

### 一画布 = 一个维度组合下的一张图

维度口径与 CMDB 一致。`region` 目前是自由文本（与 `Server.region` 同口径，留空 =
跨地域）——等地域进字典再一起改成外键，现在造一个外键会与主机上的文本对不上。

同一组合允许多张图（`ingress-path`、`db-topology`）：一张图塞两件事既排不开版也
没人看得懂。

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/api/topo/meta/` | 节点类型与关系登记表（左侧调色板数据源） | `topo` 读 |
| CRUD | `/api/topo/canvases/` | 画布元信息，支持 `?project_group=&channel=&env=&region=&keyword=` | `topo` |
| GET | `/api/topo/canvases/{id}/graph/` | 整图读取：节点（含实时状态）+ 连线 | `topo` 读 |
| PUT | `/api/topo/canvases/{id}/graph/` | 整图覆盖保存 | `topo:write` |
| POST | `/api/topo/canvases/{id}/autofill/` | 按维度自动编排，幂等 | `topo:read_create` |
| GET | `/api/topo/canvases/{id}/candidates/` | 可引用的平台资源候选，`?kind=&keyword=` | `topo` 读 |
| GET | `/api/topo/canvases/{id}/export/` | 整图导出 JSON（引用型节点用自然键） | `topo` 读 |
| POST | `/api/topo/canvases/{id}/clone/` | 按新维度克隆 | `topo:read_create` |
| POST | `/api/topo/import/` | 导入导出的 JSON；`overwrite` 需 `topo:write` | `topo:read_create` |
| GET | `/api/topo/impact/?kind=&ref_id=` | 影响面反查：该实体在哪些画布上、上下游是谁 | `topo` 读 |
| GET | `/api/topo/health/?only_issues=` | 每张画布的健康度汇总与异常明细 | `topo` 读 |

维度筛选参数「纯数字按 id、否则按 code」，与主机列表同口径。列表与详情都按登录
用户的数据范围（`common/dimscope`）收窄：范围外的画布列表看不到，直接猜 id 也
进不去（`_check_scope`）。

**不叠 sudo**：画布不改变任何人的权限，也不下发任何命令；它引用的实体在各自页面
上该有的门槛一个不少。给一张示意图加二次验证只会让人不用它。

### 整图保存为什么是覆盖式

前端画布的状态是「一堆节点 + 一堆连线」，一次拖拽可能同时改十个节点坐标、删两条
线、加一个节点。拆成 N 个 REST 子接口意味着前端要自己算 diff、还要处理「第 7 个
请求失败而前 6 个已落库」的半保存状态。整图 PUT 一次事务落库，幂等，重放安全。

代价是并发覆盖：两人同时编辑同一张图，后保存的赢。10 人内部平台不值得为此上乐观
锁——真要防，比较一下 `updated_at` 即可，字段已经有了。

**请求体口径**：`nodes` 每项必须带前端生成的 `key`（新节点还没有主键，而连线要
立刻能引用它），`edges` 的 `source`/`target` 引用这个 key；已落库的节点额外回传
`id` 以更新而非重建（主键稳定，影响面反查与审计引用的就是它）。不在入参里的节点
连同其连线一并删除；连线整体重建（它们没有对外身份，重建比算 diff 简单且不会漏）。

## 校验规则

| 规则 | 位置 | 说明 |
|------|------|------|
| `source` 与 `ref_id` 自洽 | 模型 `CheckConstraint` + `clean()` + `graph._clean_node_input` | 外部节点带 `ref_id` 会被当引用型去查实体；引用型缺 `ref_id` 则永远查不到 |
| 节点类型必须登记 | `clean()` + 整图入参校验 | 引用型只能用 `REF_KINDS`，外部型只能用 `EXTERNAL_KINDS` |
| 引用的实体必须存在 | `graph._check_refs_exist` | 否则等于允许造死链；报错指名道姓给出缺失 ID |
| 同一实体一图一次 | `UniqueConstraint(canvas, kind, ref_id)` + 保存前中文校验 | 出现两次会让影响面反查数出两条链路，而实际只有一条 |
| 连线不自环、不跨画布 | `CheckConstraint` + `TopoEdge.clean()` | 跨画布的连线在任一张图上都画不出来，属于脏数据 |
| 连线不重复 | `UniqueConstraint(canvas, source, target, relation)` | 同关系的重复连线只是把线画粗，没有信息量。**不含连接点**：同一对节点同一种关系换个方向再连一条，图上就是两条重合的线 |
| 连接点合法 | `models.HANDLES` + `TopoEdge.clean()` + 整图入参校验 | 只认 left/right/top/bottom 与空串（空 = 未指定，前端按右出左进画） |
| 画布标识唯一 | 序列化器 `validate`（关闭自动校验器） | 自动生成的唯一性校验器会要求 `region` 在 PATCH 里也必须出现 |
| 维度字典删除保护 | 外键 `PROTECT` | 项目组/渠道/环境被画布引用时删不掉 |

节点与连线刻意不用嵌套 serializer：它们只在整图 PUT 里成批出现，要能逐项指出
「第 3 个节点的类型没登记」，用嵌套 serializer 得到的是一坨按下标嵌套的字典，
运维看不懂。

### 目标维度也要在数据范围内

克隆与导入除了校验来源画布，还要校验**目标维度**（`views.dims_guard`）：范围内的图
可以被克隆成一张范围外的图，等于借克隆把数据写进自己看不见的地方。校验点在
`portable.import_graph` 的 `guard` 回调里——目标维度是「文件里的 code + 表单覆盖」叠
出来的，视图自己再算一遍必然与那里分叉；事后校验更不行，事务已提交，图已经建出来了。

`ScopeDenied` 单独一个异常类型，好让视图回 403 而不是 400：「你没权限写这里」和
「你的 JSON 有问题」对调用方是两件完全不同的事。

## 引用型节点必须与画布维度相容

`graph.dims_ok(kind, obj, canvas)` 一处定义，**三处共用**：整图保存、导入、克隆。

只有主机有维度可判（项目组/渠道/环境，画布填了地域还要对上地域）。域名 / 解析记录 /
证书身上没有维度字段，一律放行——按名字猜它属于哪个项目组，猜错的后果是「图上凭空
少一个域名」，比不判更糟。

少判一处的表现就是「dev 画布上画着生产机器」，而那种图比没有图更危险：看图的人会
照着它操作。整图保存直接报 400 拒绝（前端候选列表本来就只给同维度主机，能走到这一步
的只有手搓请求）；导入与克隆则**跳过并报告**——真正想复用的是 GA / 负载均衡那层骨架，
主机本来就该在目标环境重新挑。

## 搬运：导出 / 导入 / 克隆（portable.py）

三件事同源：都要把「引用型节点指向哪个实体」表达成**自然键**而不是主键。主键只在本库
成立——导出的图带到另一台实例、或克隆到另一组维度，`ref_id=17` 毫无意义，
`{"name": "aws-usw-p1105-01"}` 才有。

| kind | 自然键 |
|------|--------|
| `server` | 主机名（全局唯一） |
| `domain` | 域名 |
| `dns_record` | 主域名 + 主机记录 + 类型 + 值 + 线路（与 DnsRecord 唯一约束同字段） |
| `certificate` | 证书名 |

维度也用字典 `code` 而不是 id：换一台实例 id 一定不同，code 是人定的、通常一致。
导出带 `version`（当前 1）；加字段不改版本，改字段语义才加——那时导入端要能同时认旧
版，否则同事手里导出的老文件全部作废。

**克隆 = 导出后立刻导入**（带维度覆盖），不另写一套复制逻辑：两套逻辑必然在「引用型
节点怎么处理」上分叉，而这正是最容易出错的一处。

导入的收敛：同维度同标识已存在时默认拒绝（`overwrite=true` 才覆盖，且要 write 档）；
端点被跳过的连线一并跳过（留着就是一条指向空气的线）；节点**全部**落不了地时整单
报错，不留一张空画布。

连线的 `source_handle` / `target_handle` 是**纯排版信息**，不参与任何语义判定，但必须
落库：不存的话人手调好的走线保存一次就全弹回左右两侧，而「排得开」正是画布能被看懂的
前提。导出与克隆同样携带——否则克隆出来的图等于白排一遍版。

> 整图保存的顺序是**先删后建**：入参里没带 id 的节点可能引用与「即将被删的老节点」
> 相同的实体（导入覆盖走的正是这条路，它不知道对面的主键），后删就会先撞上
> `(canvas, kind, ref_id)` 唯一约束，报一条 IntegrityError 出去。

## 健康度：节点为什么是黄的 / 红的（P3）

每个引用型节点带一份 `issues`（`[{level, text}]`），节点颜色取其中**最坏一条**
（`graph._worst`）。只给颜色不给原因，看图的人还得自己去翻三个页面才知道那台机怎么了。

| kind | 判定 |
|------|------|
| `server` | 已停止 danger / 维护中 warning；**执行通道** Agent 离线或该绑未绑 danger |
| `dns_record` | 同步失败 danger / 待同步 warning；**记录已停用** warning |
| `certificate` | 失败·过期·issuing 卡死 danger；剩余 ≤15 天或待申请中 warning |
| `domain` | 已过期 danger / 即将到期 warning |
| 失联（实体被删） | danger |

两处刻意加进来的判定，都是「图上看着通、实际不通」的情形——正是画布该当场答出来的：

- **Agent 离线**：一台 NAT 主机的执行通道断了，图上看着好好的，实际什么命令都下不去；
- **解析已停用**：解析记录 `enabled=False`，图上那条线还在，实际流量根本不过来。

证书的警告阈值是 15 天（`CERT_WARN_DAYS`），与概览页的 30 天
（`CERT_EXPIRY_WARN_DAYS`）刻意不同：那边是「该续了」，这里是「快断了」，画布上 30 天
就开始黄会让图长期挂着黄色，久了没人再看。

### 汇总（health.py）

`GET /api/topo/health/` 给每张画布一份 `{total, healthy, warning, danger, lost, issues}`。

- **复用 `graph.resolve_refs`**（按 kind 批查，4 条 SQL 封顶，与画布张数无关），不为汇总
  另写 filter：第二套口径一定会和图上的颜色对不上，而「首页说 3 个异常、点进去只有 2 个
  红的」之后就没人再信这个数字。
- **只看引用型节点**：外部节点（GA、负载均衡）是手工录入的，平台不知道它们的真实状态，
  凭空给个「健康」比不给更糟——看图的人会以为那一层被监控着。
- 单独一个接口而不是塞进画布列表：列表分页且常被筛选，把遍历所有节点的代价绑上去，
  翻页也得付一次。

### 概览页联动（两个方向）

1. **画布 → 首页**：`dashboard.services.topo_alerts` 复用 `health.alert_items`，在异常区
   加一块「N 张拓扑画布存在异常节点」。条目粒度是**画布**（逐节点列会把一台机的三个问题
   铺成三行，把别的异常挤出可见范围），深链直接指进那张图。
2. **首页 → 画布**：`dashboard.services.attach_topo_links` 在**已有**异常明细（证书快
   过期、证书签发/分发卡住、域名异常、解析同步失败、Agent 离线）上标出「它在哪张链路图
   上」并给深链。首页答的是「什么坏了」，画布答的是「坏的这个东西挂在哪条链路上」，原来
   这一步要靠人自己去画布页翻。

映射表 `TOPO_REF_FIELDS` 驱动，不在各 builder 里各写一遍：builder 关心「什么坏了」，
「它画在哪张图上」是另一件事，混在一起两边都难改。三处特别处理：

- **Agent 离线**：Agent 本身不是画布节点类型，但钉死到它的主机是——看板上真正想知道的
  正是「这个 Agent 挂了，哪几条链路的机器现在下不了命令」；
- **解析同步失败**：同时查这条记录与它的主域名，按画布去重。图上可能只画了主域名，只查
  记录会让「明明画了这条链路」的图漏掉；
- **证书分发卡住**：明细按分发展示，反查用它的 `certificate_id` 与 `server_id`。

整个附加过程一次批量查（`impact.canvases_for_refs`，kind 与 id 集合过滤后在 Python 侧
剔掉笛卡尔积多出来的组合），且是**尽力而为**：外面包了 try，附加失败只记日志——概览页
是出事时最先被打开的页面，它自己必须比任何单块附加信息都稳。

两个方向都按 `topo` 模块与数据范围裁：没有画布权限、或画布不在范围内的账号，既看不到
那一块，也拿不到深链。

## 影响面反查（impact.py）

`GET /api/topo/impact/?kind=server&ref_id=12` 答「动它会波及什么」：它出现在哪些画布
上，每处的 `upstream`（谁的流量落到它身上）与 `downstream`（它指向谁）。

这是画布真正的运维价值。画得再漂亮的图，如果只能从画布那一侧打开，它就是一张挂在墙上
的画；反查让它能从**故障那一侧**被用起来——手上有一台要下线的主机时，人不会先想到
「去翻一遍拓扑图」，所以入口挂在服务器页与域名页的行操作里。

邻居节点复用 `graph.resolve_refs` / `node_payload`，名称与状态必须和画布上看到的一模
一样；并且按 kind 批量解析，一台挂在五张图上的主机不该查上几十次库。可见性同样按数据
范围收窄——反查不该成为绕过项目组范围看别人拓扑的后门。

## 自动编排（autofill）

按画布维度拉平台已有资源，**只连能确定的关系**，猜不出来的留给人手动画：

| 来源 | 生成 |
|------|------|
| 该维度（含地域）下的 `Server` | 主机节点 |
| `DnsRecord.server` 命中这些主机 | 解析记录节点 + 解析记录 --解析--> 主机 |
| 上述解析记录的 `Domain` | 主域名节点 + 主域名 --解析--> 解析记录 |
| `Certificate.domains` 覆盖这些主域名（含通配符） | 证书节点 + 证书 --关联--> 主域名 |
| `CertDeployment.server` 命中这些主机 | 证书 --落地--> 主机 |

幂等：已在图上的节点与连线跳过，人手摆好的节点不会被移动（新节点按 `kind` 分列
落位，`LAYER_BY_KIND` 即「离用户多远」）。GA / 负载均衡这类中间层由人插在解析与
主机之间。

`ServerService` 不单独出节点——一台机六个服务就是六个节点，图会直接炸掉，而且服务与
主机是从属关系不是链路关系，画成节点反而误导。它以**服务标签**的形式挂在主机节点上
（见下）。

## 主机上跑哪些服务（服务标签）

`graph._server_services` 从 `asset_mgr.ServerService` 实时读，塞进节点的
`ref.extra.services`，前端渲染成主机卡片下方的一行标签：

```json
{"name": "战斗服", "code": "battle", "status": "deployed",
 "status_label": "已部署", "process_name": "battle_server", "process_count": 4}
```

- **带上 `planned`**：图上区分「已部上」与「规划了还没部」，正是画链路时最想核对的
  一件事。`offline` 不给——已下线的服务留在链路图上是噪音。
- 排序：`deployed` 在前（那才是「现在在跑什么」），同状态按服务类型字典的 `sort_order`，
  与字典维护页看到的顺序一致。
- **卡片上显示的是进程名**（`nginx-01×4`），不是服务类型名：进程名才是这台机上实际跑的
  那个东西的标识（`ServerService.process_name`，由「服务器分配」页按「云厂商+项目组+
  环境+渠道」分组自动编号），排查时要 grep 的就是它。类型名是分类，同一类在不同机器上
  重名，写在卡片上等于没说这台机跑的是哪一个——它给 hover 与右侧面板。
- 查询走已有的 `prefetch_related('services__service_type')`，不多一次查库。
- 画布只读它，**不建第二份服务台账**——与「画布不是第五套资产台账」同一条口径，服务
  改了状态，图上刷一次就跟着变。

**规划缺口不算健康度问题**：「规划了未部署」是计划问题不是运行故障，算进 `issues` 会让
新规划的机器一上图就黄，久了没人再看颜色——与证书阈值定 15 天而非 30 天同一个理由。
这件事概览页的「服务规划三态」已经在管。
